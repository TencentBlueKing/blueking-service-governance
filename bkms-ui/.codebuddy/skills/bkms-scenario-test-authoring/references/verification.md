# 变异验证、验收与归档（步骤⑤⑥）

## 变异验证 SOP（步骤⑤）

原则：注入**用户可感知**的回归，覆盖不同保护网（回显 / 校验链 / 关键参数 / 确认流程各选一类）；每轮仅一处变异，逐轮验证。

1. **注入变异**：编辑业务源码，行内加 `// MUTATION-N:` 注释。四类代表：
   - 回显失效：编辑模式字段回显改为空
   - 校验链退化：`validateForm` 忽略子模板校验结果
   - 关键参数丢失：提交参数恒传默认值
   - 确认流程失效：确认回调恒放行
2. **跑测试**：`pnpm vitest run test/scenarios/<模块>.test.ts`，记录 failed 数与命中用例。理想态 = 只挂对应保护网用例，无误报。
3. **还原**：按 `// MUTATION-N:` 注释逐处精确改回（可用编辑工具或 `git checkout -- <file>`）；`git diff --stat -- src/` 必须为空。
4. **复跑**：确认全绿。
5. 变异实证结果记录在测试文件头「变异验证」行（命中数 / 还原确认）；**全部变异均未被捕获 = 测试无效**，回路径清单补路径。

## 验收清单（步骤⑥前逐项核对）

- [ ] 全量 `pnpm vitest run` 全绿，且本文件**连跑 3 次**结果稳定
- [ ] 本文件 tests 段 < 10s（不含冷启动编译）
- [ ] 指南 §3 全部规范逐条对照通过
- [ ] `git diff --stat -- src/` 为空
- [ ] 变异验证 ≥3 处全部被捕获，实证结果已记录

## 归档——零新增 md，不碰 ROUTES

> ROUTES 是冻结的历史台账，新模块**不进册**（是否补录由维护者决定）。归档只做两件事：

1. **测试文件头注释**：V 值、路径清单、stub/mock 边界、backlog——文件头即该模块的场景说明。
2. **`TEST_PILOT_LOG.md`**：本次踩到的、会影响后续写法的环境事实，逐行登记（根因 + 结论 + 示例位置）。

> 若后续沉淀出**跨模块可复用的新写法**，追加一行到 `bkms-ui/docs/vitest/guides/TEST_PLAYBOOK.md`。

## 提交

- 由使用者按团队规范自行提交（本 skill 不代提交）。
- 建议 message：`test: <场景名>场景级交互测试`（不带 S 编号）；body 可带用例数与 V 值。
- 提交前自检：`git status --porcelain` 干净、`git diff --stat -- src/` 为空。
