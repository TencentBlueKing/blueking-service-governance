# 特性环境

特性环境可以简单理解为一种**仅对单个应用可见的环境**。普通环境属于工作空间，可被多个应用共同使用；特性环境则归属于创建它的应用，只在该应用的部署、配置和观测等场景中展示，不进入工作空间的公共环境列表，也不能被其他应用访问。

创建特性环境类似于克隆一个已有的普通环境。用户选择源环境并提供展示名称后，平台复制源环境的基础信息和该应用在源环境中的相关配置，使新环境具备与源环境接近的初始运行条件。特性环境创建完成后独立存在，源环境后续发生变化时，不应自动影响已创建的特性环境。

创建时可控制是否复制源环境直接配置的自定义环境变量。副本保留变量名、值、描述和敏感标记，使用新记录，敏感值继续加密存储，之后两边的修改和删除互不影响。

为保证工作负载隔离，平台会为每个特性环境自动生成独立的 `namespace`，用户无需填写或维护。除 `namespace` 以及用于标识特性环境归属、来源的必要信息外，其余环境属性原则上沿用源环境。特性环境拥有独立生命周期，可单独创建和删除；删除前应先清理其中的应用部署。

## 复用来源环境的命名空间

部分纳管集群只授予了单个命名空间的权限，无法新建命名空间。创建特性环境时可传 `nsType=shared`（默认 `independent`，即新建独立命名空间），让特性环境直接复用来源环境的命名空间：

- 平台在环境记录的 `nsSharing` 子文档中生成 `resPrefix`（`f` + 4 位 `[a-z0-9]`），作为该环境所有资源名的前缀。主工作负载名为 `<resPrefix>-<应用名>`，开发模式 ConfigMap、北极星 CR 与 Service、GPA、端口池等派生资源均随之加前缀。环境/泳道作用域基础资源名的构建、还原与资源长度校验统一收口在 `pkg/core/resname`（`resname.ForEnv`、`Scope.Build` / `Scope.Restore`、`resname.Validate` 等），上层模块自行决定直接将其作为工作负载/CR 名或继续拼接各自附属后缀。
- `resPrefix` 不与来源环境的泳道名重复；应用名过长、导致带前缀的资源名超过 63 个字符时，直接拒绝创建。创建时只校验应用自身的资源（主工作负载及开发模式 ConfigMap 等派生资源）。
- 北极星 Service 名为 `<resPrefix>-<应用名>-<配置名>-polaris-service`，配置名由平台生成、固定 13 个字符，比上述资源都长。由于特性环境创建时还不在任何北极星配置的生效范围内，改为在北极星配置创建或修改生效范围时，对范围内所有环境的 Service 名做长度校验（标准环境同样适用）。
- 泳道尚未实装，`<泳道名>-<resPrefix>-<应用名>` 的长度暂不校验；泳道上线时需在泳道创建入口计入前缀长度。
- 环境集合的唯一索引为集群 + 命名空间 + `nsSharing.resPrefix`：独占命名空间的环境（`nsSharing` 缺失）之间仍然互斥，共用命名空间的特性环境以 `nsSharing.resPrefix` 区分。
- 平台不会为此类特性环境创建或删除命名空间。
- 第一期仅支持 AppModel 应用：Helm 部署，以及使用了组件的 AppModel 部署，都会被拒绝，因为平台无法保证这些资源的名称带有前缀。
- AppModel 部署、北极星 immediate 下发、GPA 下发的对象都会打上 `io.tencent.bkms.env-name` 和 `io.tencent.bkms.app-id` 标签；端口池属于环境级资源，只打 `env-name` 标签。下发前校验集群中同名对象的归属：对象属于其他环境或应用时拒绝下发；对象没有标签时，标准环境放行，共用命名空间的特性环境拒绝。校验只在命名空间确实被共用时逐个读取集群对象，即特性环境本身，或命名空间被特性环境共用的源环境（通过一次 Mongo 查询判断）；独占命名空间的标准环境只打标签，不额外请求 apiserver。
- 存在派生自某标准环境的特性环境时，该标准环境不允许被删除（须先删除关联的特性环境）；存在复用其命名空间的特性环境时，该标准环境也不能修改集群或命名空间。
- 共用命名空间的特性环境自身也不能修改集群或命名空间，需要迁移时只能重建：迁移会使其脱离来源环境，绕过"同一来源环境、同一工作空间"的共用前提，目标命名空间的环境也无法感知它的存在。
- 北极星注册的服务仍由应用级配置决定，流量隔离不在本方案范围内。
- 平台没有配额相关逻辑；若集群管理员在命名空间上配置了 ResourceQuota，特性环境会与来源环境共享这部分配额。

### 后续扩展：普通环境共用命名空间

命名规则、唯一索引、归属标签与校验、Helm/组件拒绝都只依据 `nsSharing`（`nsSharing.resPrefix`）判断，不区分环境类型，可直接沿用到普通环境。扩展时需要补齐：

- 普通环境的创建入口提供"共用已有命名空间"选项，由平台生成 `resourcePrefix`；`resourcePrefix` 只能在首次部署前确定，之后不可修改，否则资源会整体改名（Service 名变化会使调用方失效）并遗留旧资源。
- 只允许同一工作空间内的环境共用命名空间，避免按命名空间维度的查询（Pod 列表、WebConsole、日志、监控）与配额跨团队混用。
- 同一命名空间内不带 `resourcePrefix` 的环境可继续使用 Helm 与组件，带 `resourcePrefix` 的环境仍不支持，除非组件模板提供资源名前缀能力。

> 以上是关于特性环境最基础的说明，功能的更多特点，比如特性环境创建后如何管理、删除等，将在之后补充与实现。
